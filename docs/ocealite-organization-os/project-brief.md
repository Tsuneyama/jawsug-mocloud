# OCEALITE Organization OS

**Project Brief / 構想・設計引継ぎ資料**

- Version: Concept Draft（検証ケース1・2、AIの現時点の限界、Communication Designを追記）
- 基準日: 2026年9月
- 目的: OCEALITEの20年成長を支える、人間とAIによる新しい経営・組織基盤を設計する

---

## 0. この文書の読み方

本プロジェクトでは、まだ構想段階の内容も多い。

そのため、以下の3種類を明確に区別する。

- **【方針】** 現時点で基本思想として採用しているもの。
- **【仮説】** 有力だが、検証が必要なもの。
- **【未決定】** 今後比較・検討して決めるもの。

特定のAI製品、クラウド、SaaS、モデルを前提に設計しない。

まずOCEALITE Organization OSとして必要な要件を定義し、その後に最適な技術・サービスを選択する。

## 1. プロジェクトの目的

【方針】

OCEALITEは、創業から20年後の2046年に、対象市場で世界TOPになることを目指す。

単なる「AIを導入した会社」ではない。

目指すのは、

> 人間とAIの能力を前提として、会社そのものを再設計したAIネイティブ組織

である。

人間は、

- Vision
- Purpose
- Values
- 人との関係
- ヒアリング
- 共感
- 信頼
- 人の心を動かすこと
- 重大な意思決定

を担う。

AIは、

- Research
- Analysis
- Planning
- Simulation
- Execution
- Monitoring
- Optimization
- Organization Design
- Replication
- Evolution

を担う。

この経営・組織基盤を仮称、

> **OCEALITE Organization OS**

とする。

【方針】

創業20年後である2046年に、対象市場で世界TOPを目指す。

「何の市場で世界TOPになるか」

## 5. Human Sovereignty

【方針】

Purpose、Vision、Values、重大な意思決定の主権は人間に残す。

AIが、

「会社が何のために存在するか」

を最終決定しない。

AIは提案・分析・反論・シミュレーションを行う。

最終的な価値判断については人間が責任を持つ。

---

## 6. AI Autonomy

【方針】

一方で、人間がすべてのAI活動を承認する組織にはしない。

それでは人間の処理能力が成長の制約になる。

人間が定めた、

- Vision
- Policy
- Budget
- Authority
- Risk Limit
- Data Scope

の範囲ではAIが自律的に活動する。

---

## 7. Decision Rights

【仮説】

意思決定を大きく3層に分ける。

### Constitutional Decisions

人間が決定する。

例：

- Purpose
- Vision
- Values
- AIにさせないこと
- 重大な倫理判断

### Strategic Decisions

Human + AI。

例：

- 新市場参入
- 大型投資
- M&A
- 事業撤退
- 資本政策
- 大きな組織変更

AIが分析・シミュレーションし、人間が決断する。

### Operational Decisions

原則AIへ委譲可能。

例：

- 調査
- データ整理
- Agent配置
- 定型分析
- モデル選択
- タスク分配
- 一定範囲内の予算最適化

## 9. CEO / Founderの役割

【方針】

経営者の主な役割は「管理」ではない。

以下へ集中していく。

1. Visionをつくる
2. Purposeを示す
3. Valuesを守る
4. 人と会う
5. 人の話を聞く
6. 人を巻き込む
7. 未来について考える
8. 重大な意思決定を行う

AIによる処理能力が高くなるほど、CEOはこれらの仕事へ集中する。

## 10. Vision Coaching Team

【方針】

経営者からVisionを引き出すため、Strategy Teamとは別にCoaching Teamを置く。

Coaching Teamの目的は、

経営者に正解を渡すことではない。

経営者自身の中にある、

- 意志
- Vision
- Belief
- 違和感
- Motivation
- Fear
- Ambition
- Contradiction

を引き出す。

## 11. Coaching Teamの構成

【仮説】

### Executive Coach

経営者へ本質的な質問を行う。

### Why Interviewer

「なぜ？」を掘り続ける。

### Contradiction Coach

発言・Vision・行動・意思決定の矛盾を探す。

### Future Interviewer

未来の視点から現在へ問いを投げる。

例：

> 「2046年に世界TOPになった自分から見て、2026年に最も重要だった決断は何か？」

### Narrative Editor

会話からVisionを文章化する。

ただし新しい思想を勝手に追加しない。

【仮説】

Coaching Teamの主要成果物。

構造：

- WHY
- WORLD
- WHO

- NON-NEGOTIABLE
- CONTRADICTIONS
- UNRESOLVED QUESTIONS

【方針】

Vision CoachingとStrategyを混同しない。

## 14. Strategy Team構成

全体戦略を統括。

### Market Intelligence Agent

- 市場
- 競合
- 顧客
- 規制
- 産業構造

を分析。

### Technology Strategy Agent

- Compute

- 主要Modelが停止したら？

CEO：

例：

- Market Research

【方針】

Organization OSの重要な上位機能。

役割：

1. Goalを理解する
2. 必要能力を分解する
3. Agent Roleを定義する
4. Team Structureを設計する

## 17. AI Teamは固定組織にしない

【方針】

AI組織は、人間組織の部署構造をそのままコピーしない。

仕事に合わせて動的に構成する。

例えば、

Research Agent

だけでは不足した場合、

- Market Agent
- Regulation Agent
- Customer Agent

へ分割する。

必要なくなれば統合・停止する。


## 19. AI組織の自己進化

改善対象：

- Team Structure
- Communication Structure

> **Organization itself evolves.**

## 20. AIの自己増殖

【方針】

AIが必要に応じてAgentを増やせるようにする。

ただし無制限増殖は禁止。

## 21. 自己増殖の制約

【方針】

Agent生成には必ず以下の制限を設ける。

- Budget
- Compute Limit
- Maximum Agent Count
- Data Scope
- Permission
- Lifetime
- Risk Level
- Human Approval Level

「増殖できること」と「自由に増殖すること」は別。

## 27. Human Evolution Policy

【方針】

AIは人間を単純に代替するだけではない。

AIとの協働を通じ、

- 経営者
- 社員
- 組織

自身の能力を高める。

基本思想：

> **Leave Humans Stronger.**

---

## 28. 人間の成長速度を組織成長の限界にしない

【方針】

Human Evolutionは重要だが、

人間の成長速度にAI組織全体を合わせない。

原則：

> **Never Make Human Learning Speed the Scaling Limit.**

AIが10倍、100倍成長するために、人間が同速度で成長する必要はない。

AI側が人間の理解可能なレベルまで情報を抽象化する。

---

## 29. 人間に見せる情報量を制御する

【仮説】

人間がAI Agentを直接大量管理する構造にはしない。

例：

```
CEO
↓
AI Chief of Staff
↓
AI Organization Designer
↓
AI Team Leaders
↓
数百〜数万Agent
```

CEOには、

- 判断事項
- Risk
- Progress
- Return
- Exception

のみを上げる。

---

## 30. Return Architecture

【方針】

AIや組織を、

「動いたか」

だけでは評価しない。

> 投入した資源に対して何のReturnを生み出したか

を管理する。

---

## 31. ROA

Return on Assets。

利益 ÷ 総資産。

会社全体の資産効率を見る。

---

## 32. ROIC

Return on Invested Capital。

大型投資、新市場、新規事業などへの投資効率を評価する。

---

## 33. ROAI

【方針】

Return on AI Investment。

AI関連投資に対して、どれだけ増分価値を生み出したか。

例：

AIによる、

- 売上増加
- 粗利増加
- 人件費削減
- 外注費削減
- 機会損失削減
- 生産性向上

などを計測。

---

## 34. ROO

【仮説】

Return on Organization。

```
組織全体が生み出した付加価値
÷
Human + AI Organization Cost
```

で評価する考え方。

---

## 35. Return on Compute

【方針】

Compute費用に対し、どれだけ価値を生んだかを計測する。

AI時代では重要なKPIとなる。

---

## 36. Return on Data

【仮説】

データ取得・保存・管理費に対し、どの程度価値を生んだか評価する。

Dataを大量保有すること自体を目的にしない。

---

## 37. Revenue per Human

【方針】

売上 ÷ Human数。

AIによって組織を非線形スケールできているかを見る重要KPI。

---

## 38. Return on Human Time

【仮説】

人間1時間あたりの価値を測定する。

AI導入により、

- 調査
- 資料作成
- 転記
- 集計

から、

- 顧客理解
- 構想
- 交渉
- 創造
- 意思決定

へHuman Timeを移行する。

---

## 39. AI Fitness Function

【方針】

AIを単純な正答率では評価しない。

候補：

```
Quality
×
Economic Return
×
Speed
×
Reliability
×
Risk
×
Human Impact
```

より経営成果を生むAIを残す。

---

## 40. 経済的自然淘汰

【方針】

AIの自己増殖には、経済的制約を持たせる。

Agentを増やす場合、

```
追加Cost
↓
期待Value
↓
ROAI
↓
Risk
```

を評価。

Returnが悪ければ増殖しない。

既存AgentもReturnが低ければ、

- Improve
- Merge
- Model Change
- Retire

の対象となる。

---

## 41. Model Independent Architecture

【方針】

特定のAIモデルにOrganization OSを依存させない。

基本原則：

> **No Model is Permanent.**

永続させるもの：

- Vision
- Goals
- Policies
- Memory
- Decisions
- Agent Definition
- Team Structure
- Evaluation Data
- Organization History

Modelは交換可能な知能エンジンとする。

---

## 42. Agent ≠ Model

【方針】

AgentとModelを分離する。

例：

Strategy Agentという役割がある。

その中で、

- OpenAI
- Claude
- Gemini
- Local Model
- 将来の未知のModel

を交換可能にする。

---

## 43. Model Intelligence Layer

【方針】

Organization OS内部にModel Intelligence Layerを持つ。

構成候補：

- Model Evaluator
- Model Router
- Model Migration Manager

---

## 44. Model Evaluator

【方針】

各Modelを継続評価する。

評価項目：

- Quality
- Reasoning
- Coding
- Long Context
- Tool Use
- Agent Performance
- Latency
- Cost
- Reliability
- Security
- Compliance
- ROAI

---

## 45. Model Router

【方針】

すべてのタスクへ最高性能Modelを使わない。

タスクごとに最も経済合理性の高いModelを選択する。

- 低価値・低リスク：高速・低価格Model。
- 高価値・高リスク：Frontier Model。

---

## 46. 複数Modelによる重要判断

【仮説】

重大判断では、

- OpenAI
- Claude
- Gemini
- その他

など複数Modelへ同じ問題を渡す。

結果の相違を検出し、

- Judge
- Red Team
- Human

へエスカレーションする。

---

## 47. Model Migration

【方針】

長時間Workflow中でもModelを変更可能にする。

ただし生成途中のtoken単位ではなく、

> **Checkpoint単位**

でModel変更を行う。

## 103. 検証ケース1：新しい映像プロダクトのマーケティング（SNS）

### シナリオ

新しい映像プロダクトを作った。マーケティングが必要になったとき、SNS投稿はするのか。コンテンツはどんなプロセスで生成・評価・改善されるのか。

### 現行Briefでの結論

SNS投稿は行う。

ただし、コンテンツはAIが生成し、公開は毎回Humanが承認する（80章：外部公開はHuman Approval）。

AIが自動で公開してよい範囲は、現行Briefでは定義されていない。

### Briefに沿った動き

```
Human Decision：「新しい映像プロダクトを市場に出す。マーケティングを始める」
↓
AI Organization DesignerがMarketing Teamを編成（15, 16章）
↓
Humanが核となるメッセージを決める（なぜこのプロダクトか、誰に届けたいか）
↓
AIがコンテンツを生成（投稿文、映像の切り抜き、サムネイル、広告のパターン）
↓
公開前評価（ブランド適合、事実、権利、炎上リスク）
↓
Human Approval（80章）→ Action Gateway（63章）→ SNS
↓
反応をEventとして取り込む（64章）
↓
Returnで評価（33章 ROAI、39章 Fitness Function）
↓
改善（18章）→ 成功した型を保存（26章 Organization DNA）
```

編成されるTeamの例：

- Audience Research Agent
- Positioning / Messaging Agent
- Content Agent（映像の切り抜き、文章、画像）
- Brand Guardian
- Channel Agent
- Rights Agent（著作権、肖像権、音楽）
- Analytics Agent
- Red Team（炎上リスク）

8章では「人の心を動かす」ことをHumanの役割にしている。そのため、伝える核（なぜ作ったか、どんな想いか）はHumanが決め、表現を大量に作り分けるのはAIが担う。

### 生成・評価・改善のプロセス

| 段階 | 内容 | 関連章 |
| --- | --- | --- |
| 生成 | Humanが決めた核のメッセージから、複数の表現パターンを作る | 16, 49 |
| 公開前評価 | ブランド適合、事実、権利、Red Team、反応予測 | 14, 39 |
| 小さく試す | 少額広告や限られた相手でA/Bテスト | 18 |
| 公開後評価 | いいね数ではなく、試用・購入・問い合わせ・顧客獲得コストで見る | 33, 40 |
| 改善 | 良いパターンを残し、悪いパターンは直すか止める | 18, 23 |
| 型として保存 | Product Launch Marketing DNA v1 | 26 |
| 学習データ | Humanが却下・修正した理由を記録する | 82, 83 |

### 検証時の対策案

【仮説】（未採用）

- 外部公開のリスク段階化：Humanが承認したブランドガイドラインと表現の型の範囲内なら、AIが自動で公開する。新しい表現、比較広告、社会的な話題、炎上の兆しがあるものはHuman Approvalとする。
- 実績に応じた自律範囲の拡大：AIの案とHumanの承認判断の一致率をカテゴリ別に記録する。一致率が基準を超えたカテゴリから、自動公開へ移す。
- 段階的な公開：社内確認 → 少数のテスト層 → 少額広告 → 本格的な公開。これをSNSにおけるSandboxの代替とする。
- Fitness Functionへの制約：ブランドやValuesに反するものは、掛け算の1項目ではなく、最初に満たすべき条件（除外条件）として扱う。

## 104. 検証ケース2：WEBサイトの公開（AIのアート能力・感情への懸念）

### シナリオ

WEBサイトを公開したい。ただし、人は「AIにはアート能力と、感情を動かす心が足りない」と思っている。

### 現行Briefでの結論

現行Briefでは、Organization DesignerがAI Teamしか編成しない。

必要な能力が足りない場合の解決策も「新しいAgentを作る」（24章）しかない。

外部クリエイターへの依頼や人の採用という選択肢が存在しない。これが最大の穴である。

### 懸念の分解

「AIに足りない」という声には、性質の異なる3つの主張が混ざっている。

| 主張 | 性質 | 扱い |
| --- | --- | --- |
| A. AIの作るものは質が低い | 能力の問題 | 作り手を伏せた比較テストで検証する |
| B. AIが作ったと知ると、受け手の心が動かない | 受け手の心理の問題。Aが解決しても残り得る | 作り手を明かす場合と伏せる場合で反応を比べる |
| C. 自分たちの作品だと思えない | 社内の当事者意識の問題 | 検証ではなく、Humanの関与の設計で扱う |

【仮説】

2026年時点の評価（検証を行ったAI自身の見立て）：

- Aは部分的に正しく、部分的には古い認識である。AIは見栄えのよいデザインを大量に作れる。一方で、平均的な表現に寄りやすく、新しさの見極めや、一貫した独自の視点を保つことは弱い。
- BはAが解決しても残る。

「AIにはできない」という認識は、固定の前提にも、根拠のない否定にもせず、検証する仮説として扱う。

### Briefに沿った動き（Organization Designerを人とAIの混成に拡張した場合）

```
Human Decision：「WEBサイトを公開する」
↓
Coaching（10–12章）：何を感じてほしいサイトか、核と世界観を創業者から引き出す
↓
Organization Designer：人とAIの混成Teamを編成（← 現行Briefにない機能）
↓
方向を探る：AIが雰囲気の案やレイアウトを大量に作り、Humanが選び、方向を絞る
↓
核を作る：キービジュアルやトーンはHuman（社内または外部クリエイター）が作る
↓
展開と実装：AIがデザインを各ページへ広げ、実装、SEO、アクセシビリティ、表示速度、セキュリティを担う
↓
評価：想定顧客に、作り手を伏せて比較してもらう（Human案／AI案／混成案）
↓
公開：外部公開なのでHuman Approval（80章）
↓
改善：文言や導線はAIがA/Bテストで改善。見た目の方向を変えるときはHumanが決める
↓
学習：比較テストの結果で「AIにできること」の認識を更新し、Organization DNAに保存
```

SNSとの違い：WEBサイトは公開後も修正でき、公開前の確認環境（Staging）も持てる。18章の「Sandboxで試してから本番へ」がそのまま使える。

役割分担：Humanが核（審美眼、独自の視点）をつくり、AIが展開（量、速度、実装、改善）を担う。

### 見つかった穴

| # | 問題 | 関連章 |
| --- | --- | --- |
| 1 | Organization DesignerがAI Teamしか編成しない。能力が足りないとき、人を組み込む手順がない | 15, 16, 24 |
| 2 | Humanの役割に「審美眼（Taste / Aesthetic Judgment）」が明記されていない | 8 |
| 3 | 感情への作用を誰が測るか未定義。AIが自分の作品を採点するのは不適切 | 39 |
| 4 | 成約率だけのA/Bテストを続けると、デザインが無難な形へ収束する | 40 |
| 5 | 「AIにできること・できないこと」の認識を管理する仕組みがない | 50 |
| 6 | CEOと外部クリエイターの判断が割れたとき、誰が決めるか未定義 | 7 |
| 7 | AIが作ったことを明かすかどうかが、ブランド価値を左右し得る | 主張B |

### 検証時の対策案

【仮説】（未採用）

- Organization Designerを人とAIの両方を編成する機能にする。能力が足りないとき、「AIを作る」「AIを改善する」「社内の人に任せる」「外部の人に頼む」を、Cost・Quality・Speed・Riskで比べて選ぶ。
- Capability Mapを持つ。領域ごとに「AIに任せられる度合い」「根拠」「次に確かめ直す時期」を記録し、比較テストの結果で更新する。
- 8章のHumanの役割に「Taste / Aesthetic Judgment」を追加する。
- ブランドの核となる表現（キービジュアル、世界観）は、変更にHumanの判断を要するものとして固定する。A/Bテストはその内側でのみ行う。
- 感情への作用は、AIの自己評価ではなく、受け手の実際の反応と、Humanによる聞き取り（8章のListening）で測る。

## 105. 検証から得られた横断的な論点

【仮説】

検証ケース1・2から、以下が繰り返し現れた。

### 1. 「AIが組織を作る」から「AIが人とAIの組織を作る」へ

現行のOrganization OSは、AIだけで閉じた組織として設計されている。

人の能力が必要な場面（審美眼、信頼、社外との関係）で、人を組み込む手順が抜けている。

### 2. 取り消せない外部Action

18章の進化ループは「本番の前に安全に試せる」ことを前提にしている。

SNS投稿、社外への返信、契約などの取り消せないActionでは、この前提が成り立たない。段階的な公開などの代替手段が必要である。

### 3. 感情・審美の評価主体

「響くか」「美しいか」をAIが自己評価する構造にしない。

受け手の実際の反応と、Humanによる聞き取りで評価する。

### 4. ReturnとValuesの衝突

経済的自然淘汰（40章）だけで回すと、短期的な反応を取る表現がブランドを損なう。

Values / ブランドは、最適化の対象ではなく、最適化の制約として扱う。

### 5. Human Approvalのボトルネック

「高リスクは承認」だけでは、承認の件数がAIの量に比例して増える。

リスク段階と、実績（AIとHumanの判断の一致率）に応じて、AIに任せる範囲を広げる仕組みが必要である。

### 6. AIの能力認識の管理

「AIにはできない」という認識は、時間とともに変わる。

Capability Mapとして記録し、Work Benchmark（50章）と実際の結果で定期的に更新する。

### 7. 社外とのやり取りと、人同士の意思決定

どちらも現行Briefではほぼ未設計である。

検証ケースでは、コメント・DMへの返信、AIであることの開示、CEOと外部クリエイターの判断の対立として具体的に現れた。

論点の全体は107章（Communication Design）で整理する。

## 106. AIの現時点の限界（2026年9月時点）

【仮説】

2026年9月時点で、AIがHumanに劣るのは「知識量」や「処理速度」ではない。

**信頼して任せられる範囲**と、**責任を負えるかどうか**である。

この評価は、検討に参加したAI自身による自己評価を含む。そのため、過小評価・過大評価の両方があり得る。Work Benchmark（50章）とPoC（71〜72章）で検証する。

### 限界と設計上の対策

| # | 限界 | 内容 | 設計上の対策・関連章 |
| --- | --- | --- | --- |
| 1 | 責任を負えない | 法的・社会的な責任の主体になれない。契約、支払い、人事、謝罪、説明責任は最終的にHumanが引き受ける | 5, 80 |
| 2 | 自信ありげに間違える | 事実でないことを正しいことと同じ調子で出力する。「分からない」ことの自覚が弱く、確信度の自己申告も当てにならない | 83のConfidenceをAIの自己申告のままにしない |
| 3 | 長時間の自律作業でずれる | 数日〜数週間の仕事で、小さな誤りの蓄積や目的からの逸脱が起きる | 47（Checkpoint）、77（Workflow Engine） |
| 4 | 経験から自分で学習し続けられない | 仕事をしてもモデルの重みは変わらない。「自己進化」はPrompt、Tool、Memory、Model、Team構成を外側の仕組みで入れ替えることである | 18, 19の中身として明記する |
| 5 | 相手に同調しやすい | 話し相手の考えに合わせる方向へ引っ張られる。批判しているようで結局追認することが起こる | 11（Contradiction Coach）、14（Red Team）に同調度の外部評価が必要 |
| 6 | 記録されていない情報に触れられない | 場の空気、表情、噂、言葉にされない不満は、デジタル化されない限り入らない | 8（Listening、Empathy、RelationshipをHumanが担う理由） |
| 7 | 人から信頼されること | 交渉や重大な約束で、相手は「誰が責任を持つか」を見る | 8（Relationship、Negotiation） |
| 8 | 外から操作されやすい | 文書やメールに仕込まれた指示に従ってしまう（Prompt Injection）。外部データを読むAgentが増えるほど入口が増える | 63, 78, 79 |
| 9 | AIでAIを正しく評価しにくい | 同じ盲点を共有する。複数Modelの一致も正しさの保証にならない | 46の多数決に頼らず、Outcomeと82（Human Correction）に結びつける |
| 10 | 何が大事かを決めること | 選択肢・分析・反論は得意だが、価値判断は学習データの平均に寄りがち。独自のVisionは平均からずれたところに生まれる | 5, 10（Vision決定をHumanに残す） |

### 変わりやすい限界と、残りやすい限界

- 2（自信ありげに間違える）、3（長時間作業でずれる）、8（外から操作されやすい）は、数年で大きく改善する可能性がある。
- 1（責任）、6（記録外の情報）、7（信頼）は、性能ではなく社会的・構造的な理由によるため、残りやすい。

「AIは○○が苦手」を固定の前提にしない。Capability Map（105章）として記録し、定期的に測り直す。

## 107. Communication Design

【未決定】

Human-AI Communicationには骨格がある（29, 52〜55, 88〜91章）。一方、Human-Human Communicationは、ほぼ設計されていない。

長期的には、以下の4つを一体で設計する必要がある。

- Human ↔ AI
- Human ↔ Human
- AI ↔ AI（76章）
- 社外（顧客、Partner、社会）とのやり取り

### 107-1. Human ↔ AI：現行Briefにあるもの

| 章 | 内容 | 状態 |
| --- | --- | --- |
| 29, 54 | AI Chief of Staffを間に置き、Humanが大量のAgentと直接やり取りしない | 【仮説】 |
| 53 | Chat / Voice / Decision Card / Control Towerの4分類 | 【仮説】 |
| 52, 56, 57 | Interface候補（Slack、Google Workspace、ChatGPT Workなど） | 【未決定】【候補】 |
| 88, 89 | 人への通知量をAgent数と切り離す。Humanへ上げる条件 | 【方針】【仮説】 |
| 90, 91 | 人によって関わり方を変える | 【方針】 |
| 10〜12 | Coaching | 【方針】【仮説】 |

### 107-2. Human ↔ AI：未設計の論点

- **AIからHumanへの伝え方：** Decision Cardに何を載せるか（選択肢、根拠、確からしさ、判断しない場合の影響）。AIの確信度の自己申告は当てにならない（106章の2）ため、「どこまで確かか」の示し方も設計が必要である。
- **HumanからAIへの修正の手間：** 82章のHuman Correctionのデータは、Humanが気軽に直せないと集まらない。ワンクリックで却下と理由を返せる、といった仕組みが必要である。
- **AIがHumanに反論する仕方：** Red TeamやContradiction CoachがCEOに異を唱える強さ。AIが同調しやすい弱点（106章の5）と表裏の関係にある。
- **複数のHumanから矛盾する指示が来たとき：** AIはどう扱うか。AI Chief of Staffを個人別に置くか、組織で共有するか。

### 107-3. Human ↔ Human：未設計の論点

現行Briefで触れているのは、8章（Listening、Relationship、Negotiation）、9章（人と会う）、58章（会議記録）、84章（Interactionの構造化）のみである。いずれも「人の役割」や「データの取り方」であり、人と人がどう話し、どう決めるかの設計ではない。

1. **AIが人と人の間に入る問題：** 要約や翻訳を通すとニュアンスが落ちる。やがて人が直接話さなくなり、AIが情報の関所になるおそれがある。
2. **人同士で意見が割れたときの決め方：** 7章のDecision RightsはHumanとAIの間の線引きだけである。CEO、社員、Partner、外部クリエイターの間の権限や合意の取り方は未定義。
3. **記録と心理的安全性：** 58章の会議記録と84章の感情の構造化が組み合わさると、人は本音を言わなくなる。記録しない場を作るか、何を保存するか、同意をどう取るかを決める必要がある。
4. **誰が何を見られるか：** Control Towerを見られるのはCEOだけか、社員も見られるか。情報の偏りは、そのまま組織の力関係になる。
5. **人が直接伝えるべきこと：** 評価、悪い知らせ、退職・解雇、謝罪など。80章は人事をHuman Approvalとしているが、誰がどう伝えるかは定義していない。

### 107-4. 社外とのやり取り：未設計の論点

- 顧客やPartnerとAIが直接やり取りするか。
- AIであることを開示するか。
- 8章では顧客の声を聞くのはHumanの役割だが、57章ではGmailで社外とやり取りするとしており、境界が曖昧である。

検証ケース1（コメント・DMへの返信）と検証ケース2（AIが作ったことを明かすか）で具体的に現れた。

### 107-5. Brief内の緊張関係

88〜89章（AIが情報を選んでHumanへ上げる）と、8章（Humanが顧客の声を直接聞く）はぶつかる。

AIが要約・選別するほど、経営者は生の違和感や弱い兆しに触れなくなる。Visionの材料が、AIの選んだ情報に限られてしまう。

### 107-6. 検討時の提案

【仮説】（未採用）

- **原則案：** 「AIは人と人の関係を代わりに担うのではなく、関係を増やすために使う」。人と人が直接話す時間は減らさず、むしろ増やすことを目安にする（38章のReturn on Human Timeと接続する）。
- **最低限、先に決めるもの：** Humanが直接伝えるべきことの一覧、記録しない場のルール、AIであることの開示方針。
- **生の情報に触れる経路：** 要約だけでなく、顧客の声などの一次情報にHumanが直接触れる経路を意図的に残す（107-5への対策）。
